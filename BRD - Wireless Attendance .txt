1. Overview
The BLE Attendance System is a keyless, automatic attendance mechanism inspired by modern car keyless entry systems.
Employees carrying their mobile phones will be automatically marked as “present” when they enter the office and “away” when they leave — no manual action required from their side.
Attendance detection will be done using BLE beacon signals emitted by the mobile app. These signals will be picked up by ESP32 devices installed in the office, which will report to a central backend system for processing and reporting.
This POC aims to be production-grade in architecture, though limited in scope to a single office location.
________________


________________
2. Core Objectives
* Eliminate manual check-in/check-out for employees.

* Detect presence automatically using BLE beacon advertisements.

* Build a backend engine that intelligently tracks attendance, breaks, and check-outs based on presence.

* Provide HR visibility via a dashboard or API.

* Minimize power consumption on employee devices.

* Ensure system stability and reliability with minimal infrastructure.

4. Functional Scope by Component
4.1 Mobile Application (Android & iOS)
Purpose:
 Act as a BLE beacon for employee identification.
Key Functions:
   * One-time Google Workspace authentication.

   * Generate a unique employee token linked to user ID.

   * Start broadcasting this token over BLE advertising using:

      * Service UUID: 74686d62-51ac-7e8b-4a60-b0c73fbb0fbd

      * Payload: Employee-specific token (configurable rotation policy).

         * Run beacon advertising in background mode with minimal battery drain.

         * Token can be:

            * Static token during POC phase.

            * Optional daily rotation if required for security.

               * Display a simple success screen post-login with basic instructions.

               * No active check-in/out interaction required after setup.

               * Optional: app can stop advertising when user is far from office (e.g., geofence or scheduled hours).

Non-Functional Requirements:
                  * App should continue BLE advertising in background state.

                  * Power consumption should not exceed 1–2% daily for advertising.

                  * Must support both Android (foreground or background service) and iOS (CoreBluetooth background mode).

________________


4.2 ESP32 Device (BLE Scanner)
Purpose:
 Detect employee BLE tokens and forward detections to the backend.
Key Functions:
                     * Continuously scan for BLE advertisements with the Service UUID 74686d62-51ac-7e8b-4a60-b0c73fbb0fbd.

                     * On detecting a valid token:

                        * Extract token and timestamp.

                        * Identify which ESP device detected it (ESP ID).

                        * Forward this data to backend via HTTPS or MQTT.

                           * Support configurable scan interval (e.g., every 1 second).

                           * Handle multiple tokens concurrently (up to 20–50 employees in office).

                           * Stable connection to office Wi-Fi.

Payload to Backend Example:
{
  "token": "<employee_token>",
  "esp_id": "<esp_unique_id>",
  "timestamp": "<ISO_8601>"
}


Non-Functional Requirements:
                              * Device should support OTA firmware updates.

                              * Minimal local processing; business logic remains in backend.

                              * Power and network stability prioritized.

                              * No pairing or connection with phones required.

________________


4.3 Backend Server
Purpose:
 Process presence events, apply attendance rules, and store structured attendance data.
Key Functions:
                                 * Authenticate and register tokens to employees during onboarding.

                                 * Receive BLE detection events from ESP devices.

                                 * Maintain a “last seen” timestamp for each employee.

                                 * Apply business logic:

                                    * First detection of the day → Mark check-in.

                                    * Gaps > X minutes (configurable, e.g., 5 min) → Break.

                                    * Gaps > Y minutes (configurable, e.g., 30 min) → Check-out.

                                    * Continuous presence updates as long as device is detected.

                                       * Handle multiple ESP sources (multi-zone support).

                                       * Store event logs and attendance sessions in database.

                                       * Provide REST API / GraphQL for frontend and HR dashboard.

Data Model (POC level):
                                          * Employees: ID, Name, Token, Email

                                          * ESP Devices: ID, Location

                                          * Presence Events: Timestamp, Token, ESP_ID

                                          * Attendance Sessions: Check-in, Breaks, Check-out

Non-Functional Requirements:
                                             * Secure communication (HTTPS / TLS).

                                             * Basic authentication between ESP and backend.

                                             * Event deduplication logic if multiple ESPs detect the same token.

                                             * Configurable rules for break and checkout timeouts.

________________


4.4 HR Dashboard / Admin Panel
Purpose:
 Allow HR/admin users to view and export attendance data.
Key Functions:
                                                * Daily attendance view with:

                                                   * Check-in time

                                                   * Breaks

                                                   * Check-out time

                                                   * Total hours

                                                      * Filter by date, employee, department (basic).

                                                      * Export to CSV or Excel.

                                                      * Manual override for attendance (e.g., forgot phone).

                                                      * Status indicators (In / Out / On Break / Last Seen).

Non-Functional Requirements:
                                                         * Simple, responsive web interface.

                                                         * Secure login for admins.

                                                         * Fast query response time (sub-second for basic views).

5. Token & Identification Policy
                                                            * Service UUID: 74686d62-51ac-7e8b-4a60-b0c73fbb0fbd

                                                            * Token Format: Unique alphanumeric string generated at login.

                                                            * Token Rotation: Static token for POC phase.

                                                               * Optional daily rotation can be introduced in later phases.

                                                                  * ESP must ignore any BLE broadcasts not matching the UUID.

7. Security & Privacy Considerations
                                                                     * BLE tokens do not contain personal information.

                                                                     * Mapping from token to employee identity happens only in the backend.

                                                                     * All communication between ESP and backend must use HTTPS or MQTT over TLS.

                                                                     * Token is not transmitted over the network except from ESP to backend.

                                                                     * Employee phones do not talk directly to the backend after login.

________________


8. Scalability & Future Roadmap (Beyond POC)
                                                                        * Introduce rotating tokens for better security.

                                                                        * Add zone-based presence detection with multiple ESP devices.

                                                                        * Expand to multiple office locations.

                                                                        * Real-time dashboard with presence indicators.

                                                                        * Integration with payroll/HR systems.

                                                                        * AI-based anomaly detection (e.g., ghost attendance).

________________


9. Success Criteria for POC
                                                                           * 90%+ accurate check-in/check-out detection.

                                                                           * Latency of detection under 15 seconds.

                                                                           * BLE signal detection is stable for 8 hours of workday.

                                                                           * ESP uptime 95% or higher.

                                                                           * Minimal battery impact on mobile devices.

                                                                           * HR dashboard shows accurate and usable reports.
